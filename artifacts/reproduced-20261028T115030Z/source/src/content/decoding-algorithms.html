EXACT MECHANICS / DECODING

解码算法：从 logits 到一个输出 token

模型给出分数，解码器按温度、候选筛选、约束和采样规则选择输出。固定一组 logits，逐项检查候选如何被保留、重新归一化和采样。

分布与质量

解码明确改变选择规则或采样分布。它对特定任务质量的影响需要评估，单看概率更集中无法判断答案更正确。

01 / DISTRIBUTION

先声明顺序，再计算概率

操作明确规则需要声明
Greedy选择当前合法候选中分数最高者。并列规则、停止 token、约束与处理顺序。
Top-k只保留概率最高的 k 个候选，再归一化。候选少于 k 时保留全部；并列如何处理。
Top-p / nucleus按概率降序，保留累计概率首次达到阈值的最小前缀。阈值、排序、边界候选保留规则和前面的过滤。
随机采样按最终分布抽取一个候选。随机种子、采样器与其状态；同 seed 跨实现未必逐位一致。

02 / CONSTRAINTS

合法 token 取决于已有前缀与语法状态

本例的合法完整文本只有 {"ok":true} 和 {"ok":false}。候选 token 接到当前前缀后，必须仍是某个合法文本的前缀；只有完整对象后才允许 EOS。这是有限语言的显式前缀检查，不是通用 JSON grammar 引擎。

真实 tokenizer 的一个 token 可能包含多个字符、部分字符串或多个语法片段。约束引擎需要结合词表与语法状态生成 token mask；只按单字符判断容易漏掉跨字符和转义情况。XGrammar 等系统专门处理这类计算。

语法保证有适用范围

约束可以要求合法 JSON 或指定字段类型。事实正确性、外部状态和业务规则还需要独立验证；超时或长度截断可能留下未完成的前缀。

处理顺序会影响候选

先 Top-k 再做语法 mask，可能删掉所有合法候选。本例先约束再筛选；真实引擎的处理链和空候选错误处理应明确记录。

停止条件属于协议

EOS、停止字符串、最大长度与工具调用边界分别处理。停止字符串可能跨 token，终止时应明确是否保留匹配内容。

缓存跟随实际接受前缀

确定输出后才将其作为下一轮输入。修改或拒绝一段候选时，KV 状态需要与保留前缀一致。
